# Cloudflare

기기와 서버 사이에 Cloudflare를 두는 두 가지 방법과, 기준 배포가 어느 쪽을 쓰는지 설명합니다. 둘 다 필수는 아닙니다. 서버는 어떤 공급자도 이름으로 알지 못하고, [서버 실행하기](../server.md)에는 어디에도 계정이 필요 없습니다. 라우터의 포트를 열지 않고 집 밖에서 서버에 닿고 싶거나, 접근 정책이 앞에 붙은 공개 호스트 이름을 원할 때 이 페이지를 보세요.

Cloudflare의 메뉴와 요금제 조건은 바뀝니다. 아래의 각 단계는 2026-09-22 기준 Cloudflare 문서가 제시한 메뉴 경로를 그대로 적은 것입니다. 한도나 가격에 의존하기 전에 최신 페이지를 확인하세요.

## 어떤 구성인가

| 구성 | 기기가 보는 것 | 인터넷이 보는 것 | 대용량 첫 동기화 |
| --- | --- | --- | --- |
| **프라이빗 경로** (기준 배포) | Cloudflare One 클라이언트를 통한 자신의 사설 주소와 이름 | 아무것도 없음: 호스트 이름도, 열린 포트도 없음 | 사설 네트워크 트래픽으로 흐르며 공개 호스트 이름을 거치지 않음 |
| **Access가 붙은 공개 호스트 이름** | 공개 이름, Access 정책, 플러그인에 넣은 서비스 토큰 | Access 뒤의 호스트 이름 | Cloudflare를 경유하며, 대용량 파일은 공급자의 약관을 따름 |

프라이빗 경로가 기준인 이유는 서버가 계속 보이지 않고, Cloudflare 자체 문서가 대용량 전송을 그쪽으로 안내하기 때문입니다. 공개 호스트 이름 경로는 트래픽을 Cloudflare로 프록시하며, Free·Pro·Business 요금제에서는 서비스별 약관에 따라 동영상 등 대용량 파일에 유료 서비스가 필요합니다. 반면 사설 네트워크 경로는 그것을 자신의 트래픽으로 나릅니다. 어느 구성이든 대용량 첫 동기화는 LAN에서 하세요.

TLS를 종단하는 것은 무엇이든 자격 증명을 읽지만 노트는 절대 읽지 못합니다. 모든 청크와 매니페스트는 기기에서 암호화되고, 이를 복호화할 수 있는 키는 회선을 넘지 않습니다([위협 모델](../threat-model.md)). 프라이빗 경로에서 종단 지점은 당신의 네트워크 안에 있는 당신의 것입니다. 공개 호스트 이름에서는 엣지도 종단 지점이 됩니다.

## 구성 A: 프라이빗 경로와 Cloudflare One 클라이언트

서버는 자신의 네트워크 안에서 사설 주소를 유지합니다. 그 옆에서 터널 커넥터가 돌고, 경로가 어떤 주소가 그 터널 뒤에 있는지 Cloudflare에 알리며, 각 기기의 Cloudflare One 클라이언트(구 WARP)가 그 주소로 가는 트래픽을 터널로 나릅니다. 기기에 입력하는 서버 URL은 그 사설 주소로 풀리는 사설 이름입니다.

필요한 것: Zero Trust 조직("팀 이름")이 있는 Cloudflare 계정, 서버의 네트워크 안에서 터널 커넥터를 실행할 수 있는 머신, 그리고 집 밖에서 동기화할 모든 기기에 설치한 Cloudflare One 클라이언트.

1. **터널을 만듭니다.** Cloudflare 대시보드에서 **Networking** > **Tunnels**로 가서 `cloudflared` 터널을 만듭니다. 제공된 커넥터를 서버 네트워크 안의 머신에서 실행합니다. 클러스터 안의 서버 옆이거나 같은 호스트입니다.
2. **서버의 사설 주소를 터널로 라우팅합니다.** **Networking** > **Routes**로 가서 **Create route** > **Tunnel CIDR**를 고르고, 터널을 선택한 뒤 서버의 사설 주소 또는 서브넷을 입력합니다. 주소 하나면 충분하고, 서브넷은 나중에 넓힐 수 있습니다.
3. **각 기기를 등록합니다.** Cloudflare One 클라이언트를 설치하고 팀 이름을 입력한 뒤, 조직이 요구하는 로그인을 마치고 연결을 켭니다. iOS와 Android에서는 클라이언트가 VPN 프로필 설치를 요청하니 수락합니다. 기기 등록 권한은 자신의 ID만 등록할 수 있도록 설정합니다.
4. **사설 대역을 클라이언트로 보냅니다.** 클라이언트의 Split Tunnels 설정에서 2단계의 주소가 클라이언트를 통해 라우팅되는지 확인합니다. **Exclude** 모드에서는 그 주소를 포함하는 RFC 1918 블록을 제거하고 계속 제외하려는 대역을 다시 추가합니다. **Include** 모드에서는 주소나 서브넷을 추가합니다.
5. **기기에서 이름이 풀리게 합니다.** 플러그인은 입력한 서버 URL로 모든 요청을 보내므로, 그 이름이 외부에 있는 기기에서 풀려야 합니다. 호스트 이름 경로, 자신의 리졸버로 향하는 Local Domain Fallback, 또는 사설 DNS 항목을 쓰면 됩니다. 클라이언트가 라우팅하지 않는 주소로 풀리는 이름은 꺼진 서버와 똑같이 실패합니다.
6. **TLS는 직접 종단합니다.** 경로는 트래픽을 당신의 종단 지점까지 나릅니다. [서버 실행하기](../server.md)처럼 모든 기기가 신뢰하는 인증서를 가진 ingress나 리버스 프록시를 서버 앞에 둡니다. 서버는 `OBSYNC_EDGE=none`으로 실행되며, 전달된 주소는 종단 지점 자체의 대역인 `OBSYNC_TRUSTED_PROXY_CIDRS`에서 온 것만 신뢰합니다.
7. **원한다면 Gateway로 필터링합니다.** Gateway 네트워크 정책으로 등록된 기기만 서버의 주소와 포트에 닿게 하고, 그 경로의 나머지는 모두 차단할 수 있습니다.
8. **네트워크 밖의 기기에서 확인합니다.** 그 기기의 브라우저에서 서버 URL을 열고 대시보드의 로그인 페이지가 뜨는지 봅니다. 플러그인에서는 **Connection** 아래의 **Check**를 선택합니다. 한 번의 왕복으로 주소·인증서·자격 증명을 한꺼번에 증명합니다.

트레이드오프:

- 동기화하는 모든 기기가 Cloudflare One 클라이언트를 실행하며, 집 밖에서 동기화가 되려면 클라이언트가 연결돼 있어야 합니다.
- Cloudflare가 기기와 터널 커넥터 사이의 트래픽을 나릅니다. Gateway의 TLS 복호화는 꺼 두세요. 그러면 트래픽은 주소·크기·시점 외에는 Cloudflare에 불투명하며, 그것은 [위협 모델](../threat-model.md)이 어떤 네트워크 경로에도 이미 인정하는 부분입니다.
- 커넥터는 네트워크 안에서 Cloudflare로 향하는 아웃바운드 연결을 계속 열어 두는 프로세스입니다. 커넥터가 죽으면 밖에 있는 기기는 `obsync: offline`을 표시하고, LAN 쪽은 계속 동작합니다.

## 구성 B: Access 뒤의 공개 호스트 이름

서버는 Cloudflare에 있는 도메인의 호스트 이름을 얻습니다. 터널이 그 호스트 이름을 서버의 사설 주소로 공개하고, 그 앞에 Cloudflare Access가 섭니다. 대시보드용 ID 정책과 플러그인의 API 호출용 서비스 토큰입니다. 이것은 [플랫폼 온보딩](../platform-onboarding.md)이 기준 클러스터에 대해 설명하는 구성이자, 기준 배포가 채택하지 않은 구성입니다.

1. **호스트 이름을 공개합니다.** 터널 설정에서 당신의 호스트 이름(`sync.example.com`은 자신의 것으로 바꿔 읽습니다)에서 서버의 사설 HTTP 주소, 포트 8080으로 향하는 공개 애플리케이션 경로를 추가합니다. DNS 레코드는 Cloudflare가 만듭니다.
2. **Access를 앞에 둡니다.** **Zero Trust** > **Access controls** > **Applications**로 가서 그 호스트 이름으로 **Self-hosted** 애플리케이션을 만들고, 대시보드용으로 자신만 허용하는 ID 정책(예: 자신의 주소로 보내는 일회용 PIN)을 추가합니다.
3. **플러그인용 서비스 토큰을 만듭니다.** **Zero Trust** > **Access controls** > **Service credentials** > **Service Tokens**로 가서 토큰을 만들고 Client ID와 Client Secret을 복사합니다. 시크릿은 한 번만 표시됩니다. 플러그인이 쓰는 경로(`/v1/*`)에 대해 이 토큰을 포함하는 **Service Auth** 정책을 애플리케이션에 추가합니다.
4. **토큰을 플러그인에 붙여 넣습니다.** **Edge service-token headers** 아래에, Cloudflare가 부르는 이름 그대로 한 줄에 하나씩 넣습니다:

   ```text
   CF-Access-Client-Id: <the client id>
   CF-Access-Client-Secret: <the client secret>
   ```

   이 헤더는 서버 URL로 가는 모든 요청에 실리고, 다른 곳으로는 가지 않습니다.
5. **서버에 엣지 뒤에 있음을 알립니다.** `OBSYNC_EDGE=cloudflare`로 실행합니다. 이 모드에서는 모든 요청이 엣지의 연결 주소와 요청 ID 헤더를 가져야 하며, 엣지를 우회해 도착한 요청은 `421 edge_required`로 거부됩니다([문제 해결](../troubleshooting.md#edge_required)).
6. **확인합니다.** 브라우저에서 호스트 이름을 열고 Access 로그인, 그다음 대시보드가 뜨는지 봅니다. 플러그인에서는 **Connection** 아래의 **Check**를 선택합니다.

트레이드오프:

- 호스트 이름이 공개됩니다. Access가 낯선 이를 거부하고 서버도 각 기기 요청을 직접 인증하지만, 이름은 존재하고 찾아낼 수 있습니다.
- 서비스 토큰은 자격 증명입니다. 이를 가진 사람은 API의 현관까지 닿습니다. 그 뒤에는 서버 자체의 기기 인증이 남아 있습니다. 노출됐다면 Cloudflare에서 교체하세요.
- 대용량 전송은 위 약관에 따라 Cloudflare를 경유합니다. 대용량 첫 동기화는 LAN에서 하세요.
- 이 모드에서 대시보드의 기기 페이지가 주소와 국가로 표시하는 것은 엣지의 연결 주소와 국가 헤더입니다.

## 검증된 것

프라이빗 경로는 기준 배포의 경로입니다. [2026-09-14 검증](../validation-runs/2026-09-14.md)에는 그날 시험하지 않았다는 사실과 이유가 기록돼 있고, [2026-09-20 검증](../validation-runs/2026-09-20.md)에는 기준 경로에서의 기기 검증이 연결 및 TLS 확인 통과와 함께 기록돼 있습니다. 공개 호스트 이름 구성은 기록된 어떤 검증에서도 시험되지 않았습니다.
