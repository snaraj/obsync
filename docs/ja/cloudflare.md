# Cloudflare

デバイスとサーバーの間に Cloudflare を置く二つの方法と、リファレンス構成がどちらを使っているかを説明します。どちらも必須ではありません。サーバーはどのプロバイダーの名前も知りませんし、[サーバーを動かす](../server.md)にはどこのアカウントも要りません。ルーターのポートを開けずに外出先からサーバーへ届きたいとき、あるいはアクセスポリシー付きの公開ホスト名が欲しいときに、このページを読んでください。

Cloudflare のメニューやプランの条件は変わります。以下の各手順は 2026-09-22 時点の Cloudflare ドキュメントが示すメニューの経路をそのまま記しています。上限や料金に頼る前に、最新のページを確認してください。

## どちらの構成か

| 構成 | デバイスから見えるもの | インターネットから見えるもの | 大きな初回同期 |
| --- | --- | --- | --- |
| **プライベートルート**（リファレンス構成） | Cloudflare One クライアント経由で見える、自分のプライベートアドレスと名前 | 何もない。ホスト名も開放ポートもない | プライベートネットワークの通信として流れ、公開ホスト名を経由しない |
| **Access 付きの公開ホスト名** | 公開の名前、Access ポリシー、プラグインに入れたサービストークン | Access の背後にあるホスト名 | Cloudflare を経由し、大きなファイルについてはプロバイダーの条件に従う |

プライベートルートがリファレンスなのは、サーバーが見えないままでいられることと、Cloudflare 自身のドキュメントが大きな転送をそちらへ誘導しているからです。公開ホスト名のルートは通信を Cloudflare 経由にし、Free・Pro・Business プランではサービス固有の条件により、動画などの大きなファイルには有料サービスが必要になります。一方プライベートネットワークルートは、それらを自分の通信として運びます。どちらの構成でも、大きな初回同期は LAN で行ってください。

TLS を終端するものは、あなたの認証情報を読みますが、ノートは決して読めません。すべてのチャンクとマニフェストはデバイス上で暗号化され、それを復号できる鍵は回線を通りません（[脅威モデル](../threat-model.md)）。プライベートルートでは終端はあなた自身のもので、あなたのネットワークの内側にあります。公開ホスト名では、エッジも終端の一つになります。

## 構成 A：プライベートルートと Cloudflare One クライアント

サーバーは自分のネットワーク内のプライベートアドレスを保ちます。その横でトンネルコネクタが動き、ルートがどのアドレスがそのトンネルの背後にあるかを Cloudflare に伝え、各デバイスの Cloudflare One クライアント（旧 WARP）がそのアドレス宛ての通信をトンネル経由で運びます。デバイスに入力するサーバー URL は、そのプライベートアドレスに解決されるプライベートな名前です。

必要なもの：Zero Trust 組織（「チーム名」）を持つ Cloudflare アカウント、サーバーのネットワーク内でトンネルコネクタを動かせるマシン、そして外出先で同期するすべてのデバイスにインストールした Cloudflare One クライアント。

1. **トンネルを作る。** Cloudflare ダッシュボードで **Networking** > **Tunnels** を開き、`cloudflared` トンネルを作成します。表示されたコネクタを、サーバーのネットワーク内のマシン（クラスター内のサーバーの隣、または同じホスト）で実行します。
2. **サーバーのプライベートアドレスをトンネル経由にする。** **Networking** > **Routes** を開き、**Create route** > **Tunnel CIDR** を選び、トンネルを選択してサーバーのプライベートアドレスまたはサブネットを入力します。アドレス一つで十分です。サブネットは後から広げられます。
3. **各デバイスを登録する。** Cloudflare One クライアントをインストールし、チーム名を入力し、組織が求めるサインインを完了して接続をオンにします。iOS と Android ではクライアントが VPN プロファイルのインストールを求めるので、許可します。デバイス登録の権限は、自分の ID だけが登録できるように設定します。
4. **プライベート範囲をクライアント経由にする。** クライアントの Split Tunnels 設定で、手順 2 のアドレスがクライアント経由で経路制御されることを確認します。**Exclude** モードでは、そのアドレスを含む RFC 1918 ブロックを削除し、除外したままにしたい範囲を追加し直します。**Include** モードでは、アドレスまたはサブネットを追加します。
5. **デバイス上で名前が解決されるようにする。** プラグインは入力されたサーバー URL にすべてのリクエストを送るので、その名前は外出先のデバイスで解決される必要があります。ホスト名ルート、自分のリゾルバーへの Local Domain Fallback、またはプライベート DNS エントリを使います。クライアントが経路制御しないアドレスに解決される名前は、オフラインのサーバーとまったく同じように失敗します。
6. **TLS は自分で終端する。** ルートはあなたの通信を、あなた自身の終端へ運びます。[サーバーを動かす](../server.md)にあるとおり、すべてのデバイスが信頼する証明書を持つ ingress またはリバースプロキシをサーバーの前に置きます。サーバーは `OBSYNC_EDGE=none` で動き、転送されたアドレスを信頼するのは終端自身の範囲である `OBSYNC_TRUSTED_PROXY_CIDRS` からだけです。
7. **必要なら Gateway でフィルタリングする。** Gateway のネットワークポリシーで、登録済みのデバイスだけがサーバーのアドレスとポートに届くようにし、そのルート上のほかの通信をすべてブロックできます。
8. **自分のネットワークの外にあるデバイスから検証する。** そのデバイスのブラウザーでサーバー URL を開き、ダッシュボードのサインインページが表示されることを確認します。プラグインでは **Connection** の下の **Check** を選びます。一往復で、アドレス・証明書・認証情報をまとめて証明できます。

トレードオフ：

- 同期するすべてのデバイスで Cloudflare One クライアントが動き、外出先での同期はクライアントが接続済みでなければ機能しません。
- Cloudflare はデバイスとトンネルコネクタの間の通信を運びます。Gateway の TLS 復号はオフのままにしてください。そうすれば通信は、アドレス・サイズ・タイミング以外は Cloudflare からは不透明で、それらは[脅威モデル](../threat-model.md)がどのネットワーク経路にも既に認めているものです。
- コネクタはあなたのネットワーク内で Cloudflare への外向き接続を維持し続けるプロセスです。落ちると外出先のデバイスは `obsync: offline` を表示し、LAN 側は動き続けます。

## 構成 B：Access の背後にある公開ホスト名

サーバーは、Cloudflare に置いてあるドメイン上のホスト名を得ます。トンネルがそのホスト名をサーバーのプライベートアドレスへ公開し、その前に Cloudflare Access が立ちます。ダッシュボード向けの ID ポリシーと、プラグインの API 呼び出し向けのサービストークンです。これは[プラットフォームのオンボーディング](../platform-onboarding.md)がリファレンスクラスター向けに説明している構成であり、リファレンス構成が採用していない構成です。

1. **ホスト名を公開する。** トンネルの設定で、あなたのホスト名（`sync.example.com` は自分のものに読み替える）からサーバーのプライベート HTTP アドレス（ポート 8080）への公開アプリケーションルートを追加します。DNS レコードは Cloudflare が作成します。
2. **前段に Access を置く。** **Zero Trust** > **Access controls** > **Applications** を開き、そのホスト名で **Self-hosted** アプリケーションを作成し、ダッシュボード用に、自分だけを許可する ID ポリシー（例：自分のアドレスへのワンタイム PIN）を追加します。
3. **プラグイン用のサービストークンを作る。** **Zero Trust** > **Access controls** > **Service credentials** > **Service Tokens** を開いてトークンを作成し、Client ID と Client Secret をコピーします。シークレットは一度しか表示されません。プラグインが使うパス（`/v1/*`）について、このトークンを含む **Service Auth** ポリシーをアプリケーションに追加します。
4. **トークンをプラグインに貼り付ける。** **Edge service-token headers** に、Cloudflare の名前どおりに一行一つずつ入力します：

   ```text
   CF-Access-Client-Id: <the client id>
   CF-Access-Client-Secret: <the client secret>
   ```

   これらはサーバー URL へのすべてのリクエストに乗り、それ以外には送られません。
5. **サーバーにエッジの背後にいることを伝える。** `OBSYNC_EDGE=cloudflare` で起動します。このモードでは、すべてのリクエストがエッジの接続元アドレスとリクエスト ID のヘッダーを持っている必要があり、エッジを迂回して届いたリクエストは `421 edge_required` で拒否されます（[トラブルシューティング](../troubleshooting.md#edge_required)）。
6. **検証する。** ブラウザーでホスト名を開き、Access のサインイン、続いてダッシュボードが表示されることを確認します。プラグインでは **Connection** の下の **Check** を選びます。

トレードオフ：

- ホスト名は公開されます。Access は見知らぬ相手を拒み、サーバーも各デバイスのリクエストを自分で認証しますが、名前は存在し、見つけられます。
- サービストークンは認証情報です。持っている人は API の玄関まで届きます。その先にはサーバー自身のデバイス認証が残ります。漏えいした場合は Cloudflare 側でローテーションしてください。
- 大きな転送は上記の条件のもとで Cloudflare を経由します。大きな初回同期は LAN で行ってください。
- このモードでダッシュボードの「デバイス」ページがアドレスと国として表示するのは、エッジの接続元アドレスと国のヘッダーです。

## 何が実証済みか

プライベートルートはリファレンス構成のルートです。[2026-09-14 の検証](../validation-runs/2026-09-14.md)には、その日は試されなかったことと理由が記録されています。[2026-09-20 の検証](../validation-runs/2026-09-20.md)には、リファレンスルートでのデバイス検証が記録され、接続と TLS の確認に合格しています。公開ホスト名の構成は、記録されたどの検証でも試されていません。
