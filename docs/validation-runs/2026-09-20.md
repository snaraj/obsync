## Route

The reference route (docs/validation.md "Routes"): the Helm chart reconciled
by Flux on a single-node homelab cluster, the 1.0.0 release image by digest,
storage on two static local volumes, an in-cluster TLS terminator holding a
certificate from a public CA (issued through a DNS challenge, renewed by
hand every sixty days), reached only through the deployment's private tunnel
and the owner's device client. The name resolves to a private address; no
port is reachable from the internet. The deployment's own tuple (proxy,
route, certificate, policy identifiers) lives in the platform runbook, not
here.

## Privacy evidence

- From the desktop, before the device run: `/readyz` answered 200 in 0.23 s
  with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`; an unsigned
  `/v1/devices` answered 401; plain HTTP on the TLS port was not served.
- The certificate chain served is a public-CA chain that validates on the
  desktop with no private root installed on either device.
- The edge's session log shows every connection from the phone to the
  server's private address: refused by the private-range block rule until
  the policy admitted the phone, then allowed by the deployment's own rule
  and by nothing broader. The phone never had a route to the address without
  the device client.
- The vault key crossed the network only inside the device-sealed pairing
  envelope, as in the 2026-09-14 run; the server saw the claim, the
  approval, and one envelope fetch.

## Findings

All four concern the private path in front of the server, not the server or
the plugin; the plugin reported every one of them as the same message, "A
TLS error caused the secure connection to fail", or as the name not
resolving. They are recorded so the mobile troubleshooting page can name
them.

- On the home Wi-Fi with the device client off, the phone could not resolve
  the name: the router's resolver strips answers that point at private
  addresses (DNS-rebinding protection). A resolver that does not filter
  private answers, or cellular, resolves it.
- The deployment's allow rule required a device-posture check of a kind the
  edge never runs on phones, so the phone fell through to the private-range
  block rule. The owner bound a phone-capable check instead.
- The allow rule also enforced identity re-authentication after seven days;
  the phone's session was older, the edge answered "authenticate" and reset
  the flow, and the phone's client offered no working way to re-authenticate.
  The owner removed the session check from this rule only.
- For eighteen minutes the phone's device client reported itself connected
  while sending nothing through the edge, not even DNS; a manual disconnect
  and reconnect restored it. During that window the plugin's pairing attempt
  hung instead of failing.
