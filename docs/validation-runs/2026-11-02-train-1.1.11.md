# 1.1.11 train: Force sync, pairing again after a missed upgrade, desktop, 2026-11-02

One macOS desktop running the official Obsidian 1.14.5, with three vaults in one
instance driven through its own window (no file copy stands in for a user
action). The servers were two disposable `obsyncd` containers from the 1.1.10
image (`sha256:73e30fea…`), reachable on the loopback interface only, each with

## Setup

Device A ran **Set up or recover** with the server's setup token, saw the
complete backup with **Copy** and **Select** beside it, read it back and
confirmed it. Device B paired from A: both prompts showed the same code, A
approved, and B's one note went up after **Pair and upload**. Both held the
same six notes.

A then removed B with **Revoke → Rotate key**: stage, read back the new
backup, prepare with the setup token, re-encrypt, restart Obsidian, reopen
through **Resume encryption transition** (#364), commit, **Done**. A ended
active with the old key kept as history. B, after its restart, read: "This
device was removed from your server. Your notes and vault key are safe here.
Pair it again from a device that still syncs: obsync settings, Pair this
device."

## Force sync (#369)

A device out of step was made by closing Obsidian, removing one note and its
record, and opening Obsidian again. It started `idle` and stayed without the
note through **Sync now**: the feed had nothing to send it again.

| Build | Result |
| --- | --- |
| build-369 | **Force sync** brought the note back in 0.45 s, with the same bytes, and saved. The renderer then stayed at 100% CPU: the button never came back, and DevTools could not evaluate `1+1` in that window. With the debugger attached before the press, the pause landed in Obsidian's `BaseComponent.then` (`function(e){ return e(this), this }`). The button's `.finally(() => button.setDisabled(false))` handed the component to a promise, which resolved it to itself without end. The test fakes had no `then`, so the suite could not see it |
| build-369b and 1.1.11 | The note back in 0.47 s, the same bytes, the button enabled again, every renderer idle. Answer: "in step with the server: checked 5 files here and 7 on the server; sent 0, received 1." A second press: "…checked 6 files here and 7 on the server; sent 0, received 0." On the device that had paired again: "…checked 8 files here and 9 on the server; sent 0, received 0." On an unpaired device: "This device is not paired yet. On a device that already syncs this vault, choose Pair a new device, then paste its code in obsync settings with Pair this device." |

The server count includes folder records.

## Not covered here

- **The physical phone.** A candidate build reaches a phone only through a
  download served from the laptop, and this run opens no listener beyond
  loopback. The phone journey (#370's own case: a suite-1 device that the
  encryption upgrade removed, then Force sync) runs on the published 1.1.11
  through Community plugins, and its record follows.
- **A legacy start against a real server.** The legacy device told to pair
  again (#370) is covered by tests against the fake server; the phone journey
  above is its live case.
