# Validation run 2026-09-21: user-journey scenarios on 1.0.3

Second device run against the reference deployment, one day after the
[2026-09-20 run](2026-09-20.md). That run proved pairing and the two basic
edit directions over the private route. This run works through what a person
does with a vault in a day: creating, editing, renaming, moving and deleting
notes and folders on either device, closing and reopening the app, large
attachments, and recovery. Every scenario ran on real devices against the
production server with disposable content in one test folder.

Scope, route and platform coverage are stated by class, as in the previous
record. Nothing about the deployment's configuration, addresses, device
identity or the owner's notes is recorded here.

## Devices and versions

| Role | Platform class | Plugin |
| --- | --- | --- |
| Desktop | macOS desktop | 1.0.3, installed from the community directory |
| Phone | iOS phone | 1.0.1, installed at pairing; the in-app update journey is scheduled against 1.0.4 |

Both devices sync the whole vault. The route is the private connectivity
path described in [`kubernetes.md`](../kubernetes.md).

Observations outside the numbered scenarios:

- Closing the vault window on the desktop stops sync for that vault with no
  notice; the dashboard's last-seen time is the only signal. Obsidian
  plugins only run while their vault is open. Documented in troubleshooting.
- While the history dialog was open, the status bar reported a repair error
  that pointed the user at connectivity and the server's scrub report; the
  server's scrub was clean and the cause was a device-side scheduling
  collision. #103

## What this run proves and does not prove

Proven: create, edit, delete and bulk operations converge in both directions
within seconds over the private route; large files take the documented
per-platform path; the startup reconcile pushes work done while the app was
closed; hidden paths and links stay out of sync.

Not proven: recovery through the history dialog on a journal of this size;
folder deletion originating on the phone; behaviour with the phone offline
(airplane mode was not exercised); any scenario on Android, Windows or Linux.

## Findings filed from this run

- #96 rename deletes the note on every device (P0, fixed in 1.0.4)
- #98 offline edits overwritten silently on relaunch (P0, fix in progress)
- #99 growing-file guard published a mid-copy snapshot
- #100 remote-only classification leaves a stale local copy in place
- #101 external move takes minutes to sync
- #102 restore-from-history pacing
- #103 false repair error during the history dialog

Until 1.0.4 is installed on every device, do not rename notes or folders in
a synced vault. Until the fix for #98 ships, open the app on a device before
editing there if the same notes were edited elsewhere while it was closed.
