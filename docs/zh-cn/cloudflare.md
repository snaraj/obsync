# Cloudflare

在你的设备和你的服务器之间放置 Cloudflare 的两种方式，以及参考部署采用的是哪一种。两者都不是必需的：服务器不认识任何服务商的名字，[运行服务器](../server.md)也不需要在任何地方注册账号。如果你想在外出时不在路由器上开放端口就能访问服务器，或者想要一个前面带访问策略的公开主机名，就看这一页。

Cloudflare 的菜单和套餐条款会变化。下面每一步给出的菜单路径都是 Cloudflare 文档在 2026-09-22 的写法；在依赖某个限额或价格之前，请核对最新页面。

## 选哪种方式

| 方式 | 设备看到什么 | 互联网看到什么 | 大体量首次同步 |
| --- | --- | --- | --- |
| **私有路由**（参考部署） | 通过 Cloudflare One 客户端看到的你自己的私有地址和名称 | 什么都没有：没有主机名，没有开放端口 | 作为私有网络流量传输，不经过公开主机名 |
| **带 Access 的公开主机名** | 一个公开名称、一条 Access 策略、插件里的一个服务令牌 | Access 背后的主机名 | 经 Cloudflare 代理，大文件受服务商条款约束 |

私有路由之所以是参考方式，一是服务器始终不可见，二是 Cloudflare 自己的文档就把大体量传输引向这条路：公开主机名路由把流量经 Cloudflare 代理，而在 Free、Pro 和 Business 套餐下，服务专项条款要求视频等大文件使用付费服务；私有网络路由则把它们当作你自己的流量传输。无论哪种方式，大体量首次同步都请在局域网内完成。

无论由什么终止 TLS，它都会读到你的凭证，但永远读不到你的笔记：每个数据块和每个清单都在设备上加密，能解密它们的密钥从不经过网络（[威胁模型](../threat-model.md)）。在私有路由上，终止点是你自己的，位于你的网络之内。在公开主机名方式下，边缘节点也是一个终止点。

## 方式 A：私有路由加 Cloudflare One 客户端

服务器保留你自己网络中的私有地址。旁边运行一个隧道连接器，一条路由告诉 Cloudflare 哪些地址在这条隧道后面，每台设备上的 Cloudflare One 客户端（原 WARP）把去往这些地址的流量送进隧道。设备里填写的服务器 URL 是一个解析到该私有地址的私有名称。

你需要：一个带 Zero Trust 组织（"团队名"）的 Cloudflare 账号，服务器网络内一台能运行隧道连接器的机器，以及每台要在外出时同步的设备上安装的 Cloudflare One 客户端。

1. **创建隧道。** 在 Cloudflare 控制台进入 **Networking** > **Tunnels**，创建一个 `cloudflared` 隧道。把它给出的连接器运行在服务器网络内的一台机器上：集群里服务器旁边，或者同一台主机。
2. **把服务器的私有地址路由进隧道。** 进入 **Networking** > **Routes**，选择 **Create route** > **Tunnel CIDR**，选中隧道，填入服务器的私有地址或子网。一个地址就够；子网以后可以扩大。
3. **注册每台设备。** 安装 Cloudflare One 客户端，输入团队名，完成你的组织要求的登录，然后打开连接。在 iOS 和 Android 上客户端会请求安装 VPN 描述文件，请允许。把设备注册权限设置为只有你自己的身份才能注册。
4. **让私有网段走客户端。** 在客户端的 Split Tunnels 配置里，确认第 2 步的地址经由客户端路由。在 **Exclude** 模式下，删除包含它的 RFC 1918 网段，再把仍想排除的网段加回去；在 **Include** 模式下，加入该地址或子网。
5. **让名称在设备上能解析。** 插件把每个请求都发到你填写的服务器 URL，所以这个名称必须在外出的设备上能解析：一条主机名路由、指向你自己解析器的 Local Domain Fallback，或者一条私有 DNS 记录。解析到客户端不路由的地址的名称，会像离线服务器一样失败。
6. **自己终止 TLS。** 路由把你的流量送到你自己的终止点：服务器前面的 ingress 或反向代理，带有每台设备都信任的证书，和[运行服务器](../server.md)里一样。服务器以 `OBSYNC_EDGE=none` 运行，只信任来自 `OBSYNC_TRUSTED_PROXY_CIDRS`（即终止点自身网段）的转发地址。
7. **可选：用 Gateway 过滤。** 一条 Gateway 网络策略可以只允许你注册过的设备访问服务器的地址和端口，并拦截这条路由上的其他一切。
8. **从网络之外的设备验证。** 在那台设备的浏览器里打开服务器 URL，应该看到控制面板的登录页。在插件里选择 **Connection** 下的 **Check**：一次往返同时证明地址、证书和凭证。

取舍：

- 每台同步的设备都要运行 Cloudflare One 客户端，客户端连上之后外出同步才能工作。
- Cloudflare 承载设备与隧道连接器之间的流量。请让 Gateway 的 TLS 解密保持关闭；这样流量对它而言除地址、大小和时间之外都是不透明的，而这些是[威胁模型](../threat-model.md)对任何网络路径本来就承认的。
- 连接器是你网络里的一个进程，持续保持一条到 Cloudflare 的出站连接。它一旦掉线，外出的设备显示 `obsync: offline`，局域网内则照常工作。

## 方式 B：Access 背后的公开主机名

服务器得到一个你放在 Cloudflare 上的域名下的主机名。隧道把这个主机名发布到服务器的私有地址，前面站着 Cloudflare Access：控制面板用身份策略，插件的 API 调用用服务令牌。这是[平台接入](../platform-onboarding.md)为参考集群描述的方式，也是参考部署没有采用的方式。

1. **发布主机名。** 在隧道配置里添加一条已发布应用路由，从你的主机名（`sync.example.com` 代表你自己的）指向服务器的私有 HTTP 地址，端口 8080。DNS 记录由 Cloudflare 创建。
2. **把 Access 放在前面。** 进入 **Zero Trust** > **Access controls** > **Applications**，在该主机名上创建一个 **Self-hosted** 应用，并为控制面板添加一条只允许你本人的身份策略，例如发到你自己地址的一次性 PIN。
3. **为插件创建服务令牌。** 进入 **Zero Trust** > **Access controls** > **Service credentials** > **Service Tokens**，创建一个，复制 Client ID 和 Client Secret；密钥只显示一次。为插件使用的路径（`/v1/*`）给应用添加一条包含此令牌的 **Service Auth** 策略。
4. **把令牌粘贴到插件里。** 在 **Edge service-token headers** 下按 Cloudflare 的命名逐行填写：

   ```text
   CF-Access-Client-Id: <the client id>
   CF-Access-Client-Secret: <the client secret>
   ```

   它们随每个发往服务器 URL 的请求一起发送，不会发往别处。
5. **告诉服务器它在边缘节点后面。** 以 `OBSYNC_EDGE=cloudflare` 运行。在该模式下每个请求都必须携带边缘节点的连接地址和请求 ID 头，绕过边缘节点到达的请求会被以 `421 edge_required` 拒绝（[故障排查](../troubleshooting.md#edge_required)）。
6. **验证。** 在浏览器里打开主机名，应先看到 Access 登录，再看到控制面板。在插件里选择 **Connection** 下的 **Check**。

取舍：

- 主机名是公开的。Access 会拒绝陌生人，服务器也仍然自己验证每个设备请求，但这个名称存在，而且可以被发现。
- 服务令牌是一份凭证。持有它的人能到达 API 的大门；服务器自身的设备认证仍然守在后面。一旦泄露，请在 Cloudflare 里轮换。
- 大体量传输按上述条款经 Cloudflare 代理。大体量首次同步请在局域网内完成。
- 在这种模式下，控制面板"设备"页显示的地址和国家，就是边缘节点的连接地址和国家头。
